## Summary

After the config entry is reloaded (Settings, Devices & services, Easy Sidebar Pro, Reload; or any
unload + setup), every browser that was already open keeps receiving data from the old, discarded store.
In those browsers a saved layout snaps back to the previous one right after Done, and a folded group
unfolds itself, although the server stored the change. Live default updates to other users are stale
the same way until each browser is refreshed.

## Steps to reproduce

1. qa_admin: open HA in a browser; the sidebar shows groups.
2. Reload the entry: `POST /api/config/config_entries/entry/<entry_id>/reload` (or the UI menu).
3. Without refreshing that browser, open the editor, drag the Energy dashboard above מצלמות, click Done.

## Expected

The open browser shows the saved order (PROJECT.md *Business outcomes*: "every open browser of that user
updates live"). SPEC §3.1 asks for a browser refresh only after install / removal, not after a reload.

## Actual

The open browser shows the old order after Done; `.storage/easy_sidebar_pro` holds the new order; a
browser refresh shows the new order. Reproduced twice (once with a fold, once with a save).

## Evidence

```
before                     [dash-cameras, dash-kids, home, G, ..., good-days, dash-energy-home]
reload                     200 {"require_restart":false}
after Done (open browser)  [dash-cameras, dash-kids, home, G, ..., good-days, dash-energy-home]
stored order               ["dash-energy-home","dash-cameras","dash-kids","home","g:qyfqa9o9",...]
after browser refresh      [dash-energy-home, dash-cameras, dash-kids, home, G, ...]
```

Fold case: after the reload, a click on the group header unfolds it locally; within 400 ms it shows
folded again (the old store's `collapsed`), while the stored `collapsed` is `[]`.

Failing test: `tests/test_qa_regressions.py::test_bug_010_subscription_survives_entry_reload` fails with
`open subscription got stale data: {'layout': None, 'default': None, 'own': False, ...}`.

## Screenshots

![Open browser after Done still shows the old order](https://github.com/bareli/easy_sidebar_pro/blob/main/qa/evidence/BUG-010-open-browser-shows-old-order-after-save.png?raw=1)

## Likely root cause

Proven by the failing test: `ws_subscribe` captures `store` in the `send` closure. `async_setup_entry`
creates a new `LayoutStore` on reload; the existing dispatcher subscriptions stay connected and call
`old_store.view(...)` whenever the new store fires `SIGNAL_UPDATED`.

## Relevant files

- `custom_components/easy_sidebar_pro/websocket.py` (`ws_subscribe.send`)
- `custom_components/easy_sidebar_pro/__init__.py` (`async_setup_entry`, `async_unload_entry`)

## Recommended remediation

In `send`, read the current store from `hass.data[DATA_STORE]` at call time and skip sending when it is
absent.

## Fix prompt

In `websocket.py`, change `ws_subscribe` so the `send` callback looks up `hass.data.get(DATA_STORE)` each
time it runs and returns without sending when it is None. Acceptance:
`tests/test_qa_regressions.py::test_bug_010_subscription_survives_entry_reload` passes and the existing
suite still passes.
