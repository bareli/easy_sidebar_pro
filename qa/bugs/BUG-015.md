## Summary

Group name, icon and line colours are mixed toward the theme's text colour so they reach 4.5:1 / 3:1 on
the sidebar background. That adjustment is computed only when the sidebar renders. Switching between
light and dark while the page is open (the profile's theme picker, or HA's "auto" mode following the
operating system at dusk / dawn, which wall tablets commonly use) does not re-render the sidebar, so the
colours tuned for the previous theme stay on screen until something unrelated re-renders it (an entity
state change, navigation). On a quiet system that is open-ended: on the dev instance the stale colours
were still shown after 30 seconds, with "Cameras" at **1.63:1** on the light sidebar and "Info" at
**2.48:1** on the dark one. A page loaded directly in either theme is correct (6/6 loads).

## Steps to reproduce

1. As qa_admin with a layout that has coloured groups (the v0.3 admin default on 8190: Home `red`,
   Cameras `amber` with icon `teal`, Info `#3f51b5`), load the page in dark mode.
2. Profile > Theme > Light (or `home-assistant` `settheme` `{dark:false}`), touch nothing else.
3. Wait 30 s and read the group names' computed colour; then switch back to dark and wait 30 s again.

## Expected

SPEC §7.1: "the frontend resolves the colour and the sidebar background / text of the current theme
(re-read when `hass.themes` changes) and mixes the colour ... 4.5:1 for the name, 3:1 for icons and
lines". The colours should be recomputed for the new theme as soon as it applies, as they are on a fresh
load.

## Likely root cause

`Controller.palette()` is only consulted from `render()` (`look()` -> `palette()`), and the sidebar does
not render on a theme change: HA's `ha-sidebar.shouldUpdate` compares `panels`, `panelUrl`, `user`,
`localize`, `locale`, `states`, `userData` (and a few own properties) but not `themes`, and the v0.3
`shouldUpdate` patch adds nothing for it (it only honours the controller's `dirty` flag). The cache key
(`this.pal.themes === hass.themes`) is therefore never re-checked until an unrelated re-render.
Supported by: 0 sidebar updates in 30 s after the switch, and correct colours right after a navigation.
What would prove it: make the patched `shouldUpdate` return true when `hass.themes` changed and observe
the colours update within one frame.

## Relevant files

- `custom_components/easy_sidebar_pro/www/easy-sidebar-pro.js`: `Controller.palette()`, `look()`,
  `render()`, `patch()` -> `p.shouldUpdate`
- HA frontend `src/components/ha-sidebar.ts` `shouldUpdate` (reference)

## Recommended remediation

Trigger a refresh when `hass.themes` changes (for example in the `shouldUpdate` patch, or when the
controller receives a new `hass`), and read the palette after HA has applied the theme variables (a
microtask / next frame after the change), so the probe does not read the old values. The item-level
`--esp-own-*` variables set in `afterUpdate` come from the same `groupLooks` and follow automatically.

## Regression test

Browser check: load light, switch to dark, wait 1 s, assert each group name's computed colour equals the
value from a fresh dark load (and reverse). No pure JS unit test can see this.

## Fix handback (2026-10-01, commit 5b48d95)


Cause confirmed as recorded: the patched `ha-sidebar.shouldUpdate` never looked at `hass.themes`. Fix (`www/easy-sidebar-pro.js`, `patch()` -> `p.shouldUpdate`): when the controller has a palette and `hass.themes` is a different object, drop the palette and return true; the next render re-reads the theme and recomputes every `look()` (group header vars and the item-level `--esp-own-*`). Unrelated hass updates keep HA's own rule (same `themes` object -> false). HA applies the theme variables before replacing `hass.themes`, so the re-read sees the new values (measured below).
